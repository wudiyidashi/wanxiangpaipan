# Research: 大六壬核心排盘与古籍对照审校

- Query: 审核月将、天盘、四课、十二天将、九宗门三传及基础神煞的实现完整性、古法一致性、模型契约与测试证据，区分确认缺陷、项目锁定口径和流派争议。
- Scope: mixed
- Date: 2026-07-28

## Findings

### 1. 结论摘要

当前核心排盘并非整体不可用：天盘旋转公式、四课构造以及九宗门三传主体均已实现；三传实现与项目锁定规范大体一致，两个定向测试套件也全部通过。但测试全绿掩盖了三类会传播到用户结果的事实错误：

1. **高：月将在中气当日、实际交节时刻之前提前换将。** 这会改变天盘，并连锁改变四课、三传、天将和分析结果。
2. **高：十二天将把昼夜选择贵人与顺逆布将混为一事，且地盘/天盘键语义互相冲突。** 当前实现的“双重反转”使神将相对贵人实际上始终按同一方向排列；四课/三传与圆盘 UI 又用不同语义查询同一张表。
3. **高：神煞只固定生成 15 项，其中模型位置类型、月德、天医、丧门、吊客等与所核《六壬大全》口径不符。** 错误数据直接进入 UI、AI formatter 和“神煞落三传”分析。

此外，四课计算本身正确，但 `Ke`/`SiKe` 注释错误；不传天将配置时，四课和三传会把所有乘神静默伪造为贵人；公开服务对非法或不完整天盘映射缺少契约校验。九宗门的主要风险不在主干缺失，而在未覆盖的阴阳分支、涉害逐层决胜和缺乏独立古例。

### 2. 审核口径与证据等级

- **确认的实现缺陷**：可由当前代码、依赖实现或同一数据结构的消费者矛盾直接证明，不依赖选择哪一派古法。
- **相对项目规范的正确性**：以 `.trellis/spec/domain/daliuren-pan-engine.md` 的已锁定口径判断；即使古籍另有异说，也不在本报告中擅自改判。
- **相对所核古籍的差异**：主要对照《六壬大全》卷一“起例”和《六壬存验》公开转录；转录用于定位与算法审查，尚未满足父任务“回到馆藏影印页核验”的最终引文标准。
- **流派选择**：贵人法、天喜、涉害孟仲止法、刚日别责取法等存在传承差异，只登记差异和需要做出的产品决策，不把单一转录包装为唯一古法。

### 5. 确认缺陷，按严重度排序

#### 5.1 高：月将在中气日提前换将

`YueJiangService.getYueJiangByDateTime` 的注释明确要求“最近已经发生的中气”（`yue_jiang_service.dart:75-78`），但实现先调用 `lunar.getCurrentQi()`，命中即返回（`84-87`），之后才调用精确的 `getPrevQi()`（`89-91`）。

项目锁定 `lunar 1.7.8`（`pubspec.lock:515-522`）。该版本：

- `Lunar.getCurrentQi()` 只比较年、月、日，不比较时分秒（本机 pub cache `lunar-1.7.8/lib/calendar/Lunar.dart:1151-1159`）。
- `getPrevQi()` 经 `_getNearJieQi` 默认比较 `toYmdHms()`，会尊重精确交节时刻（同文件 `1045-1051,1060-1105`）。
- 依赖自身测试给出 2022 年谷雨为 `2022-04-20 10:24:18`（`lunar-1.7.8/test/JieQi_test.dart:99`）。

因此 `2022-04-20 09:00` 尚在春分后的戌将区间，当前代码却因日期命中谷雨而返回酉将。该错误每个中气日都会影响交节前的一段时间，且月将是后续整盘的旋转基准。修复口径应以精确 `getPrevQi()` 为唯一主判，围绕交节前一秒、交节时刻、交节后一秒补测试。

#### 5.2 高：十二天将方向与落盘语义错误

**双重反转是可由代码直接证明的内部错误。** 昼课使用正序神将表并让支索引 `+i`；夜课同时使用逆序神将表（`daliuren_constants.dart:305-335`）并让支索引 `-i`（`shen_jiang_service.dart:41-66`）。两个反转互相抵消：无论昼夜，贵人相邻的同一方向都仍是螣蛇，当前映射没有真正实现自身声称的“夜课逆布”。

**方向判据也不应直接等于昼夜。** 《六壬存验》转录的起例说明：昼夜用于选阳贵/阴贵；选出的天盘贵人支落到地盘后，落在亥子丑寅卯辰则顺行，落在巳午未申酉戌则逆行，并特意说明“以天盘之贵而临地盘”“非是十二神中有顺逆”（转录第 329 行）。当前服务在 `shen_jiang_service.dart:28-44` 直接用昼夜决定顺逆，且没有先在天盘 map 中反查贵人所临地宫。

**同一 map 被两种互斥语义消费。** `ShenJiangPosition.diZhi` 和 `diZhiToShenJiang` 的文档都定义为地盘位置（`shen_jiang_config.dart:14-18,58-59`）；圆盘也按地盘支查询（`daliuren_pan_disk_dialog.dart:332-336`）。但四课用上神，即天盘支查询（`si_ke_service.dart:134-140`），三传也用传支查询（`san_chuan_service.dart:637-643`）。若 map 的键真是地盘支，四课/三传错；若键其实是天盘支，UI 和模型文档错。服务同时又计算 `tianPanZhi = tianPanMap[diZhi]`（`shen_jiang_service.dart:64-74`），使位置对象再错映射一次。

现有贯通例 `2026-04-18 22:20` 的阴贵卯实际落地盘辰，按上述《六壬存验》规则本来就需要顺行；当前恒顺实现恰好得到例中数值，却仍断言 `directionDescription == 夜课逆布`（`daliuren_system_test.dart:244-283`）。这个例既不能证明逆布实现，也反而暴露标签和数据不一致。

修复前需先定贵人底本口径，再把至少两张映射分开：`天盘支 -> 神将` 供四课/三传，`地盘宫 -> 神将` 或可推导的位置表供圆盘；方向应记录实际顺逆，不能复用 `isYangRi` 表示昼夜。

#### 5.3 高：神煞模型与多项公式不成立

`ShenShaService` 声称“30+种”（`shen_sha_service.dart:4-7`），实际每次固定生成 15 项：5 吉神（`42-96`）、6 凶神（`107-167`）、4 中性神（`178-218`）。`shiZhi` 从未参与计算；`riGan` 虽传入三个 helper，却在 helper 内完全未使用（`18-29,35-39,100-104,171-175`）。

模型只允许 `ShenSha.diZhi` 表示“所临地支”（`shen_sha.dart:19-20`），但天德表会返回丁、壬、辛、甲、癸、丙、乙、庚等天干，月德当前永远返回丙、壬、甲、庚（`shen_sha_service.dart:223-248`）。这不仅是命名问题：`ShenShaChuanService` 只做 `shenSha.diZhi == chuan.diZhi`（`shen_sha_chuan_service.dart:25-29`），所以干神永远不能落传。formatter 测试甚至把这种错误契约锁成“天德临壬、月德临壬”（`daliuren_formatter_test.dart:134-135`）。

与本次所核《六壬大全》卷一相比，至少有以下明确差异：

| 项目 | 当前代码 | 《六壬大全》转录 | 判断 |
|---|---|---|---|
| 天德 | 月建查混合干支表（`223-239`） | “天徳丁坤壬辛亥甲癸寅丙乙己庚”（第 159 行） | 表意大体同类，但模型必须能表达天干/卦位/地支，不能一律叫 `diZhi` |
| 月德 | 寅午戌丙、申子辰壬、亥卯未甲、巳酉丑庚（`242-248`） | “月徳巳寅亥申三轮”（第 161 行） | **使用了另一套常见命理表，不符合该六壬起例** |
| 天喜 | 按十二月逐位戌亥子丑……（`251-267`） | “春戌夏丑秋辰冬未”（第 167 行） | **有传承差异，需定源，暂不武断判错** |
| 驿马 | 按日支三合局（`270-276`） | 支马表子丑寅卯……对应寅亥申巳循环（第 127-134 行） | **吻合** |
| 天医 | 月建前一位（`279-283`） | “天医子卯午酉三轮”（第 173 行） | **不符** |
| 丧门 | 以日支驿马代替（`295-298`） | 岁煞，“岁前二辰”（第 47-73 行） | **起例维度和公式均错；当前 API 缺年支** |
| 吊客 | 丧门对冲，仍由日支起（`300-304`） | 岁煞，“岁后二辰”（第 47-73 行） | **起例维度和公式均错；当前 API 缺年支** |
| 劫煞、灾煞、华盖、将星 | 按日支三合局计算（`306-345`） | 卷一列入十二支神煞体系（第 127-153 行），但本转录此处未展开全部表值 | **体系方向合理，尚未逐值完成影印本核验** |
| 白虎、天狗、天罗、地网 | 月建对冲/月序或固定支（`288-293,322-325,348-352`） | 本次定位材料不足以确认当前具体表 | **不得视为已验证正确** |

完整性同样不足。《六壬大全》卷一至少列出日德、日禄、三奇（第 91-125 行）；项目用户文档还承诺“德神、禄神、马星、桃花、破碎、五鬼等”（`docs/大六壬排盘案例.md:38-42`）。当前没有日德、日禄、三奇、桃花、破碎、五鬼。应先把位置建模为有类型的“天干/地支/干支日/其他宫位”，并记录起例依据（年、月、季、日干、日支、时），再谈扩充数量；直接往现有 `diZhi` 字符串继续塞表会扩大错误传播。

#### 5.4 中：缺省乘神被静默伪造为贵人

`SiKeService._createKe` 和 `SanChuanService._createChuan` 都先把乘神设成 `ShenJiang.guiRen`，只有传入配置且查询成功才覆盖（`si_ke_service.dart:134-140`; `san_chuan_service.dart:637-643`）。因此调用公开服务时省略配置、配置键语义错误或查无此支，结果都不是“未知”，而是确定但虚假的贵人。

生产 `DaLiuRenSystem` 正常路径确实传入配置（`daliuren_system.dart:150-172`），所以这不是当前主编排每课都全为贵人；但 13 个三传黄金例全部省略配置（`san_chuan_service_test.dart:16-28`），生成的乘神均为伪值且没有断言。契约应改为强制配置、可空乘神或显式 unknown/error，不能用有术数含义的值兜底；同时需评估 `.trellis/spec/domain/daliuren-pan-engine.md:33-36` 的 JSON 兼容冻结要求。

#### 5.5 中：公开服务未维护天盘 map 与地支输入不变量

- `getDiZhiIndex` 对非法地支返回 `-1`（`daliuren_constants.dart:355-356`）；`arrangeTianPan` 未验证月将和时支，仍会算出看似正常的旋转 map（`tianpan_service.dart:24-46`）。
- `getTianPanZhi` 和三传 `_tianPan` 查无键时直接返回输入支（`tianpan_service.dart:87-94`; `san_chuan_service.dart:602-605`），把缺数据伪装成伏吟式同位。
- `SiKeService.isFuYin` 与 `SanChuanService._isFuYin` 都只遍历现有 entries，空 map 会真空地返回 `true`，部分同位 map 也会被视为完整伏吟（`si_ke_service.dart:157-168`; `san_chuan_service.dart:579-587`）。反吟检查有同类完整性问题。

主系统当前会构造完整合法 map，因此这是 API/维护性风险而非已观察到的生产错盘。服务入口至少应验证十二个合法且一一对应的地支键值。

#### 5.6 低：四课模型文档与真实公式冲突

实际构造为：一课 `干上/干`，二课 `干阴/干上`，三课 `支上/支`，四课 `支阴/支上`（`si_ke_service.dart:30-47`），符合项目规范 `daliuren-pan-engine.md:12-15`。

但 `Ke` 总注把二、三课顺序写错（`ke.dart:7-10`）；`SiKe` 把二课写成日干寄宫、四课写成日支本位（`si_ke.dart:7-14`）；`Ke.xiaShen` 又声明永远是“地盘地支”（`ke.dart:20-21`），而第一课下神实际是日干。算法无需按这些错误注释修改，应修正文档/类型语义。

### 6. 九宗门逐法审计

《六壬大全》卷一起例第 9-43 行依次列出贼克、比用、涉害、遥克、昴星、别责、八专、伏吟、返吟。`SanChuanService` 的分派顺序和各 helper 位于 `san_chuan_service.dart:94-154,157-574`，总体复现了项目 spec 的九法。

#### 6.1 别责穷举旁证

本次按 60 个合法日柱 × 12 种完整天盘位移独立枚举四课上神数，得到恰好 9 个“四课不全、无近克、无遥克”的别责配置：

`丙辰 s=1`、`丁酉 s=10`、`戊辰 s=1`、`戊午 s=1`、`辛丑 s=3/9`、`辛未 s=3/9`、`辛酉 s=11`。

这与《六壬大全》第 29-31 行“刚三柔六共九课”及列举日课一致，也支持代码用“四课上神四位各异”判断四课全（`san_chuan_service.dart:390-393`）。这是结构枚举旁证，不替代每一例的古籍成盘核验。

#### 6.2 反吟规范漂移

《六壬大全》第 43 行明确写“六日该无尅，丑未同干丁己辛”，即丁丑、己丑、辛丑、丁未、己未、辛未六日。项目 spec 却写“仅丁丑/己丑/丁未/己未”（`daliuren-pan-engine.md:29`），漏辛丑、辛未。

代码没有硬编码四日清单；只要完整反吟且四课无克，就走通用井栏射分支，因此结构上没有跟随这条错误 spec 限制。但当前测试只覆盖己丑（`san_chuan_service_test.dart:138-143`），应先补辛丑、辛未等六日参数化例，再修正文档，避免未来按 spec “修坏”现有通用实现。

### 8. 流派与来源决策点

#### 8.1 贵人法不能只修一个布尔值

《六壬存验》第 329 行提供了“昼夜选贵、落宫定顺逆”的清楚算法，可用于暴露当前内部错误；但《六壬大全》提要第 9-13 行同时指出传本“说多岐”，并特别批评书中天乙贵神阴阳顺逆仍沿俗例。项目当前只提供 `classic` 与甲日昼夜互换的 `jiaDayAlt`（`daliuren_constants.dart:416-429`），并不足以表达不同底本的完整贵人表和顺逆法。

因此确认项是：当前双反转、坐标混用和标签不一致必须修。未决项是：默认贵人表及顺逆法最终以哪一底本为准、是否配置化。规划必须先登记底本和例盘，再冻结默认。

#### 8.2 天喜

当前十二月递进表与《六壬大全》“春戌夏丑秋辰冬未”不同；另有流传表采用逐月戌亥子……。在未确定产品底本前，天喜标记为“来源待决”，不是确认代码错误。

#### 8.3 已锁定的三传分歧

项目 spec 已显式锁定涉害孟仲之后是否继续刚柔、刚日别责取合干寄宫上神还是寄宫本位、八专有克课体标注等分歧（`daliuren-pan-engine.md:23,26-27`）。当前代码按 spec 实现；除非父任务重新选源，不应把这些作为 bug 顺手改动。

### 9. 建议修复顺序与最小验收

1. **先修月将精确交节**：这是确定、局部且会改变整盘的错误；以 2022 谷雨精确时刻建边界回归。
2. **再重构十二天将坐标契约**：先确定底本，再拆分天盘乘将与地盘落宫映射；补四类顺逆交叉盘及 UI/四课/三传贯通断言。
3. **重建神煞位置和起例类型**：先解决干/支和年/月/季/日维度，再修月德、天医、丧门、吊客；同步修 formatter、落传分析和历史 JSON 兼容策略。
4. **消除伪造缺省值和 map 静默降级**：非法输入应失败或显式 unknown；完整性检查放在公开服务边界。
5. **补九宗门分支矩阵与外部古例**：尤其涉害三级平局、阴阳对偶分支和反吟六日；修正 spec 的反吟日数。
6. **最后修文档与声明**：更正 `Ke`/`SiKe`/`ShenJiangConfig` 注释、神煞“30+”和用户文档能力清单，避免实现与展示再次漂移。
