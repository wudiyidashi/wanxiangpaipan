- Query: 基于现有核心排盘审校、分析/UI/AI 跨层审校、古籍证据源清单和当前仓库代码，建立覆盖完整大六壬体系的可实施能力矩阵；逐项记录古籍主基线、现状、缺陷或缺口、目标状态、实现边界、验证方式和优先级。

## Findings

### C00 冻结状态（2026-07-28）

- 已建立 `assets/data/daliuren/classics/` 证据目录、四类 schema、固定数量门禁和覆盖报告；当前总计 474 条规则，238 条神煞、64 条课经、100 条毕法。
- 神煞为 233 adopted、2 disputed、3 excluded；课经 64 adopted；毕法 99 adopted、1 disputed。三族均为目录/证据采用，`executableApproved=0`，不得被后续任务直接当成 typed 算法。
- 三张《大六壬指南》影印课例达到 B/approved，其中重审与涉害各有独立完整盘；内部 13 位移盘只保留为 C 级结构回归。
- 《大六壬断案》《六壬存验》公开检索仍只有 locator-only 文本，四张候选课例保持 C/pendingScan；未用转录冒充影印证据。
- C00 之后，C04-C14 必须逐家族把所需 C/D 条目核到 B 并补正反 fixture 后才能设置 `executableApproved=true`；目录 adopted 不等于产品实现批准。

### 1. 总体判断

当前仓库已经具备一条可运行的“大六壬 v1”链路：四种起课入口生成历法信息、月将、天盘、四课、三传、十二天将和 15 项神煞；结果运行时派生 15 个格名映射、干支主客/三传/神煞标签、十行项目裁决表与日支级应期候选，并同时进入 UI、AI formatter 和 JSON 持久化。

这条链路距离父 PRD 所定义的“完整古法体系”仍有明显层级差距：

- **基础事实层有阻断性错误**：月将交节提前、十二天将方向与坐标契约错误、神煞位置模型和多项表值错误。
- **九宗门主体存在，但证据和分支覆盖不足**：13 例均为内部合成位移盘；反吟无克 spec 漏掉辛丑、辛未。
- **传统派生层大部缺失**：三传遁干、旺相休囚死、完整神煞、六十四课经、毕法百法、类神占类、本命行年尚未形成领域模型或计算服务。
- **断课层只完成项目 v1**：当前十行裁决与多数措辞明确是项目约定，不是《大六壬指南》已逐条核定的传统断法；应期只有地支日候选，没有日历日期和缓急尺度裁定。
- **跨层已有真实产品表面，但缺少规则版本**：UI、AI 和历史记录能消费当前盘；保存结果没有 schema/pan-engine/rule-set 版本，旧错盘会被当前分析器无标识地继续解释。

父 PRD 已选择一次性完整交付，并锁定分层单一基线（`prd.md:30,34`）。下表中的 P2/P3 仅表示依赖顺序，不表示延期到任务外。

### 2. 基线、状态与优先级

#### 2.1 分层主基线

| 层级 | 主基线 | 使用规则 |
|---|---|---|
| 起例、月将、天地盘、贵人/十二天将、四课三传、神煞、六十四课经、毕法赋 | 《钦定四库全书·六壬大全》十二卷 | 默认规则必须回到明确卷次和影印页；公开转录只作定位。 |
| 断课、类神、占类、年命、应期 | 《大六壬指南》 | 以核定影印页建立规则；书中未覆盖处才进入补缺流程。 |
| 外部完整课例 | 《大六壬断案》《六壬存验》 | 只用于独立验证，不反向覆盖主底本规则；异文登记。 |
| 补缺与异文 | 《壬归》《六壬粹言》《大六壬探原》等 | 仅在主基线缺项时采用，并显式记录来源等级与冲突。 |
| 历法、时间、存储、随机/报数入口 | 现代产品契约 | 古籍给规则语义，现代历法库、时区、schema 和交互必须另有可测试的软件契约。 |

证据等级沿用 `classics-source-inventory.md`：A=影印页+可复算课例并有交叉底本，B=单一影印页或多底本一致，C=现代校注/项目手推，D=无版本 OCR/代码现状/转载。A/B 才可成为确定性古法规则；C 只辅助测试设计。

#### 2.2 状态

- **已实现**：存在生产数据路径，不等同于古籍已验证。
- **部分实现**：主路径存在，但字段、分支、证据或消费面不完整。
- **确认错误**：可由代码内部矛盾、依赖行为或已定位规则直接证明。
- **项目 v1**：有明确软件行为，但来源是项目约定而非已核古法。
- **未实现**：仓库搜索未发现领域模型、计算服务或有效消费路径。
- **待核源**：当前材料不足以判定对错，不能按代码现状宣称正确。

#### 2.3 优先级

| 优先级 | 含义 |
|---|---|
| P0 | 会改变基础盘、产生互斥结论、伪造事实或使历史数据不可识别；阻断所有下游扩展。 |
| P1 | 建立规则、证据、类型和版本的基础契约；后续知识模块依赖。 |
| P2 | 父任务要求补齐的传统知识与高级分析能力；必须在 P0/P1 稳定后实现。 |
| P3 | 完整呈现、文档和体验收口；不得用于掩盖上游未完成。 |

### 11. 实现依赖与验收闸门

完整交付应按事实依赖推进，而不是按页面模块并行堆功能：

1. **证据与版本骨架**：先建立 source/evidence/rule ID、typed cast context 和历史版本策略。没有这些，64课/毕法等新增规则无法审计，旧盘也无法区分。
2. **P0 基础盘修复**：精确月将、手动输入契约、validated TianPanMap、贵人落宫/顺逆、双坐标天将、禁止伪造贵人。
3. **传统派生事实**：旬空/遁干/旺相/完整关系、typed 神煞和核定表值。断课只能消费这一层产出的事实。
4. **知识规则目录**：六十四课经、毕法百法、类神占类、本命行年；每一模块都先证据目录，再 evaluator，再 UI/AI。
5. **传统断课与应期**：在稳定 facts 和占类之上重建《指南》规则；保留项目 v1 的兼容版本直到新规则通过外例。
6. **跨层收口**：统一 fixture 验证 domain、UI、AI、JSON 和历史迁移；修正文档并发布可观察的版本变化。

每项能力只有同时满足以下条件才可标“完成”：

- 有稳定 rule/capability ID、明确输入输出和所有权层；
- 有主底本卷页、证据等级、采用口径与异文记录；
- 有至少一个可失败正例和反例，分支型算法覆盖所有可达路径；
- UI、AI 和持久化不会丢失或改变领域事实；
- 历史版本行为可识别，必要时可迁移或显式重排；
- 不以现有代码结果、OCR 或 AI 推断反向证明古法正确。
