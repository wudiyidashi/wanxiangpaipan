# 设计：大六壬完整体系与古籍证据化实现

## 1. 设计目标

本父任务把当前“能排盘、能给出项目 v1 分析”的实现提升为可审计、可版本化、可由古籍课例回归的大六壬完整体系。目标不是把古籍文字堆进 UI，而是建立一条可复核的数据链：

```text
馆藏影印页
  -> 版本化证据登记与异文裁决
  -> 稳定 ruleId 的结构化规则目录
  -> 基础盘事实
  -> 神煞/课经/毕法/类神/本命行年等规则命中
  -> 证据化断课与应期
  -> UI、AI、历史记录的一致呈现
```

所有子任务共享本设计。子任务可以细化内部实现，但不能改变底本优先级、证据等级、版本兼容和跨层一致性约束；如确需改变，必须先回到父任务更新设计并重新评审。

## 2. 规则底本与证据模型

### 2.1 分层单一基线

- 《钦定四库全书·六壬大全》：月将、天地盘、贵人神将、神煞、九宗门、六十四课经、毕法赋的主底本。
- 《大六壬指南》：课体、断课组合和占断主依据。
- 《大六壬断案》《六壬存验》：外部完整课例和实占验证。
- 《壬归》《六壬粹言》《大六壬探原》：主底本缺项、异文和解释补充。
- 现代校注、固定转录和 OCR 只用于检索，不直接升级为古籍事实。

### 2.2 证据等级

| 等级 | 定义 | 产品行为 |
|---|---|---|
| A | 明确版本的影印页、可复算课例，并有独立底本交叉支持 | 可作为默认古籍规则 |
| B | 单一明确影印页，或多底本规则一致但缺完整课例 | 可实现，必须有边界测试并显示具体版本 |
| C | 现代校注、项目推演或固定转录 | 只能辅助解释和测试设计 |
| D | 无版本转载、OCR 原文、现有代码行为或模型推断 | 不得作为古籍规则实现依据 |

### 2.3 规范化规则条目

每条规则至少包含：

- `ruleId`：稳定、不可由展示词派生的机器标识，例如 `dlr.pan.yuejiang.zhongqi-boundary`。
- `name`、`category`、`scope`：显示名、能力类别和适用层。
- `sourceRefs`：底本 ID、馆藏标识、卷次、影印页/叶、必要短引文和解释。
- `evidenceLevel`、`traditionVariant`：证据等级与异文标识。
- `conditions`、`priority`、`exclusions`：适用条件、优先级和互斥关系。
- `expectedEffect`：结构化结果，不用中文展示词驱动执行。
- `fixtures`：至少一个独立预期值或古籍课例引用。
- `engineSince`、`deprecatedBy`：规则版本边界。

扫描件本体不入库。仓库保存结构化登记、短引文、馆藏定位和推演记录。OCR 文本必须保留 `locatorOnly=true`，生成器和测试禁止把它当作最终引文。

### 2.4 规则目录形态

采用“规范化 JSON 源数据 + 生成的强类型 Dart 目录”：

- `assets/data/daliuren/classics/` 保存 source、rule、fixture 等结构化 JSON。
- `tool/daliuren_classics/` 负责 schema 校验、重复 ID 检查、引用完整性检查和 Dart 目录生成。
- `lib/domain/services/daliuren/classics/generated/` 只保存生成结果，领域服务保持同步、纯函数和无 I/O。
- `test/fixtures/daliuren/classics/` 保存与生产匹配算法独立的外部课例输入和预期结果。

生成检查必须能发现手写生成文件漂移、六十四课经不是 64 条、毕法不是 100 条、缺页码、悬空 sourceRef、重复 ruleId 和无 fixture 的确定性规则。

## 3. 领域边界与数据契约

### 3.1 分层边界

- 排盘事实层：历法、月将、天地盘、四课、三传、贵人神将、神煞、遁干、旺相、本命行年。这里不得产生“可成/难成”结论。
- 经典规则层：六十四课经、毕法赋、类神和占类规则，只根据有类型的事实匹配，输出 `ruleId` 命中和证据。
- 分析层：按《大六壬指南》及已登记组合规则形成因素、条件、冲突裁决和应期；项目启发式必须显式标为项目规则。
- 呈现层：只格式化结构化事实和规则命中，不解析中文文案反推业务条件。

领域服务继续遵守 `lib/domain/services/daliuren/` 的纯静态服务约定；共享模型只在确有跨术数语义时进入 `shared/`，大六壬专属证据和课经模型保留在本系统内。

### 3.2 共享规则元数据

新增大六壬专属的稳定契约：

- `DlrRuleRef`：`ruleId`、规则版本、证据等级、sourceRefs。
- `DlrRuleHit<T>`：命中规则、结构化依据、结果、冲突状态和显示摘要。
- `DlrRuleConflict`：互斥规则、采用规则、裁决原因；不得靠列表先后静默吞掉反例。
- `DaLiuRenAnalysisReport` 增加 `analysisRuleVersion`、`sourcePanVersion`、`compatibilityStatus` 和结构化规则命中。

旧的中文 `term` 可以保留为兼容显示字段，但所有执行分支改用枚举或 `ruleId`。展示文案变更不得改变裁决结果。

### 3.3 基础盘契约修正

- 月将以精确交节时刻为边界，不再按交节日期提前换将。
- 十二天将拆分“昼夜选贵”“贵人支”“贵人所临地盘宫”“顺逆”“天盘支乘将”“地盘宫落将”六个概念；四课/三传和圆盘分别使用明确 map。
- 神煞位置使用有类型位置（天干、地支、宫位或无固定位置）及起例维度，禁止把天干塞进 `diZhi`。
- 三传补齐遁干、旺相休囚死、与日干完整关系；旧 `isWangXiang` 如需保留，只作为从完整状态派生的兼容 getter。
- 手动四柱输入必须验证柱间约束，自动月将必须与可确定的起课时刻绑定；不能确定时要求明确手动月将。
- `birthYear` 只有在本命/行年链路真正消费后才作为有效产品输入。

### 3.4 经典能力输出

- 六十四课经以恰好 64 个目录条目为完整性门槛；每条可有多个结构化命中条件和异文，但默认口径唯一。
- 毕法赋以恰好 100 个法则目录条目为完整性门槛；一课可同时命中多法，输出确定的优先级、互斥和组合关系。
- 类神按用户所选占类解析，并可结合三传、神将、神煞、本命行年；未选择占类时不得伪造类神结论。
- 本命、行年缺必要输入时输出“未计算”状态，不使用默认性别或猜测出生信息。
- 断课以结构化事实和经典命中为输入。现有 v1 十行表在完成古籍裁决前保留为 `project-v1` 兼容规则，不能冒充《指南》原法。

## 4. 版本与历史盘策略

### 4.1 新记录

`DaLiuRenResult` 增加向后兼容字段：

- `panEngineVersion`：生成盘面的引擎版本。
- `evidenceCatalogVersion`：所用证据目录版本。
- `castInputSnapshot`：规范化、可重放的起课输入，包括方法特有原始输入和随机结果/种子。
- `recastFromId`：新盘若由旧盘重排，记录来源 ID。

分析规则版本属于运行时报告，不把完整分析报告持久化；但报告必须声明它解释的是哪个盘面版本。

### 4.2 旧记录

- JSON 缺版本字段时反序列化为明确的 `legacyUnknown`，不得默认成当前版本。
- 旧盘继续可查看，UI 和 AI 均显示旧口径/版本未知警示。
- 当前分析器若解释旧盘，必须在报告中带兼容性警示，不能表现为现行规则生成的事实。
- 只有原始输入充分、可确定性重放时才提供“按当前规则重排”。重排新建记录、保留旧记录并写 `recastFromId`。
- 旧报数缺原始数字、旧电脑起课缺随机种子时，不推断或补造输入，不提供“原样重排”。

该方案优先采用 result JSON 的可空/默认字段实现，不为大六壬单独破坏通用数据库表；如实现研究证明必须改 schema，子任务须补迁移、降级和回滚测试。

## 5. 起课参数与用户交互

- 占类改为明确的选项集，不以自由文本驱动规则。
- 本命/行年所需的出生年、性别等输入均为显式可选参数；缺项时相应模块停用并说明原因。
- 传统应期需要的事类紧急程度或时间尺度采用枚举/选项，不从问题文本猜测。
- 重要流派配置只保留“证据充分、会实质改变盘面、且有用户价值”的选项；其他异文只显示证据说明。
- 新增参数必须有旧 JSON 缺字段测试和默认行为测试。

## 6. UI 与 AI 一致性

- 结果页按“版本/警示、基础盘、经典命中、断课因素、应期、证据详情”的信息层次展示；不在卡片内再嵌套卡片。
- 神煞必须展示吉、凶、中性完整集合；规则详情可查看来源，但不在主盘堆叠长引文。
- AI `coreData` 分开输出 `yueJian` 和 `yueJiang`，并结构化输出规则 ID、证据等级、版本、命中依据、冲突和兼容状态。
- UI、人类可读 AI 文本、机器可读 AI 数据和领域报告使用同一份报告对象；“无解/可填实”等互斥语义只能有一个裁决结果。
- 所有新增区域覆盖窄屏、长中文规则名、空态、旧版本警示和大量命中的滚动/折叠行为。

## 8. 测试与质量门槛

### 8.1 测试分层

- 目录校验：schema、数量、ID、sourceRef、页码、证据等级、fixture 完整性和生成同步。
- 规则单测：表驱动逐条规则，预期值来自证据登记或独立手算，不复制生产算法。
- 边界矩阵：节气秒级边界、昼夜贵/顺逆四类、九宗门阴阳与多级决胜、神煞各起例维度。
- 完整盘课例：至少使用《断案》《存验》中的外部课例贯通基础盘到断课，内部合成例只用于补穷举边界。
- 契约测试：旧 JSON、新 JSON、历史警示、重排新建、UI/AI/coreData 一致性。
- Widget 测试：窄屏、长文本、空态、中性神煞、版本警示和经典规则详情。

### 8.2 完成定义

- 64 课经和 100 毕法条目数量、引用和逐条测试全部通过，不能用占位条目凑数。
- 每个声称“古籍规则”的行为至少达到 B 级证据；否则降级为项目规则或不输出确定性标签。
- 所有子任务各自通过定向 analyze/test 和 codegen 同步检查。
- 最后一次父级复核运行全量 `flutter analyze` 与 `flutter test`，生成完善度报告，并复查 UI/AI/历史记录数据流。

## 9. 兼容、发布与回滚

- 新字段一律先以可空或旧值默认反序列化，旧记录读取是硬性回归门槛。
- 先引入规则契约和版本标识，再修改会改变盘面的算法；避免新旧事实无法区分。
- 每个子任务独立提交并可 `git revert`；生成目录、schema 和运行时变更必须在同一子任务内保持同步。
- 若某条古籍规则在影印核验中证据不足，回滚该规则到“未验证/不启用”，不能回滚整个证据框架。
- 最终集成前保留现有 v1 字段的兼容读取；删除旧字段或旧 formatter 键必须另有明确迁移任务，本父任务默认不做破坏性删除。
